## Pipeline bugs

1. **--max-gb not respected for zip-range with large members (shoulder-3d-us-mosaicking).** Repro: `uv run waila-validate --only shoulder-3d-us-mosaicking --worker x --pilot 100 --max-gb 2 --redo`. The report says n_media=35, bytes=1.84 GB, but raw/ grew to ~3.7 GB (70 x 52.8 MB `.raw` volumes plus `.mhd` headers) before prepare; byte accounting under-counts by ~2x. Cache stayed within cap, but a 2 GB per-dataset budget is not a reliable bound for this strategy.
2. **Registry-hard vs metadata conflicts are silent (piur-thyroid-segmentation).** submodality hard='3d ultrasound' from registry and 'b-mode ultrasound' from DICOM code give `conflicts: 84` in the report yet registry wins with no review row. Repro: `uv run waila-validate --only piur-thyroid-segmentation --pilot 100`; see `labels.submodality.conflicts`.
3. **review_values rows carry class=NaN (piur-thyroid-segmentation).** dicom:ImageType values appear in review with a bare NaN class serialised into the report JSON (not null); harmless but breaks strict JSON parsers.
4. **Label-only record selected as downloadable (gomez-embryo-updated-labels-auckland).** A doi-routed figshare record that lists only `Gomez w empties.csv` was in selection; select could drop CSV-only records automatically.
5. **Processing order differs from --only order** (cosmetic): progress counters [k/N] do not follow the list order.
